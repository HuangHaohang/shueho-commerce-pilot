本轮修复有明确代码证据的并发、故障恢复、同办公网络限流和生成报告质量问题。
Commerce Pilot仍基于OpenAI开源Codex Harness；没有自制Agent循环，没有自动
重放模型/付费供应商调用，也没有提高真实客户额度。

## 已完成

| 领域 | 当前行为 |
| --- | --- |
| App Server | 并发共享完整初始化；旧进程退出不会清除新进程请求 |
| SSE | 每连接1MiB缓冲、30秒持续背压边界；只断开慢订阅，不中断任务 |
| 浏览器恢复 | 重连合并权威读回；请求及正文15秒上限；切任务取消旧读取 |
| 数据库 | scope初始化从4条SQL合并1条；短断连不崩溃；回滚失败销毁连接 |
| 外部仓库 | 保持10连接，等待最多5秒；固定脱敏错误消息；不自动重放SQL |
| 模型目录 | 并发请求合并、2MiB正文上限和完整deadline；401/403清缓存且不重试 |
| 报告质量 | 缺依据、置信/决策矛盾或评分错误标“待复核”；保留正文与证据 |
| 公司同NAT入口 | GET/HEAD与写请求分桶，公开静态独立处理，保留写保护和内部隔离 |
| Windows | 逐个验证11个受管Hook；不可变导入重放必须经过精确内容readback |

字符串长度在原生schema中提供指导，接收端继续硬校验；数组使用`maxItems`。
不把文本指导称为模型硬截断，也不假设所有自定义Provider支持同一约束。
[官方Structured Outputs文档](https://developers.openai.com/api/docs/guides/structured-outputs)
说明了支持子集及fine-tuned模型差异；实际Provider/model仍需上线前验证。

## 真实数据库并发结果

Windows、Node24.14.0、Docker PostgreSQL16；独立可丢弃库，100个合成用户、
同一20连接池。每轮每用户20次事务，三轮交替执行旧四语句scope初始化与当前
真实RLS helper，总计12000次事务，每次检查tenant/workspace/user及自己的成员关系。

| 轮次 | 基线事务P95 | 优化后事务P95 | P95下降 | 基线/候选错误 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 185.3 ms | 120.7 ms | 34.8% | 0 / 0 |
| 2 | 224.2 ms | 103.0 ms | 54.1% | 0 / 0 |
| 3 | 353.7 ms | 188.2 ms | 46.8% | 0 / 0 |

这只衡量事务访问与等待，不包含HTTP、SSE、模型服务或生成内容。基线重现旧
事务初始化路径，并非完整旧版应用；机器有其他开发活动，不能外推生产极限吞吐。

  8个行为测试全部执行；没有真实Qwen/Elasticsearch/供应商验收。

- 实际React hook与Edge受控故障：5次重连合并1次历史读取；正文、活动、图片、
  原生问题及终态恢复；15秒读取停滞、切任务取消和旧请求竞争均通过。
